> 角色：成员三 —— 行程规划与调整 Agent

## 一、三位成员分工概览

| 成员 | 核心职责 | 核心输入 | 核心输出 |
|------|---------|---------|---------|
| **成员一** | 对话入口、意图识别、需求提取、工作流编排、前端集成、Chatbot/RAG 封装 | 用户自然语言 | `RecommendationContext` → 给成员二和成员三 |
| **成员二** | 景点/酒店/餐厅推荐、高德 POI 搜索、路线规划、地图可视化 | `RecommendationContext` | `Place[]`、`RouteResult[]` → 给成员三 |
| **成员三（你）** | **行程规划、预算计算、硬约束校验、软偏好评价、修改调整、版本管理** | `Place[]` + `RouteResult[]` | `Itinerary`、`BudgetSummary`、`TripDiff` |

---

## 二、整体数据流

```
用户输入
   ↓
成员一：识别意图 → 提取需求 → 分离硬约束/隐含偏好
   ↓  传给成员二  RecommendationContext
成员二：推荐景点/酒店/餐厅 → 规划路线
   ↓  传给成员三  Place[] + RouteResult[] + RecommendationContext
成员三：生成行程 → 校验硬约束 → 评价软偏好 → 输出结果
   ↓  传给成员一
成员一：组织最终回复 → 返回前端展示
```

三种一级意图：

| 意图 | 流程 |
|------|------|
| **新建行程** `create_trip` | 成员一 → 成员二 → 成员三 → 前端 |
| **修改行程** `modify_trip` | 成员一 → 成员三（必要时调成员二获取替代地点）→ 前端 |
| **旅游问答** `travel_qa` | 成员一 → RAGService → 前端 |

## 三、你的模块如何与其他成员合并

### 3.1 合并方式：接口对接

你的两个核心入口：

```
PlanningAgent.plan()
  输入来自成员二：places, routes, hard_constraints, semantic_preferences
  输出给成员一：itinerary, budget, evaluation, trace

AdjustmentAgent.modify()
  输入来自成员一：ModificationRequest
  输出给成员一：itinerary, diff, evaluation
```

### 3.2 已准备好的合并点

| 合并点 | 代码位置 | 说明 |
|-------|---------|------|
| 接收成员二推荐结果 | `agents/planning_agent.py:plan()` 的 `places`、`routes` 参数 | 成员二的输出直接传参 |
| 接收成员一硬约束/软偏好 | `agents/planning_agent.py:plan()` 的 `hard_constraints`、`semantic_preferences` | 从 `RecommendationContext` 提取 |
| 修改行程时调成员二 | `clients/recommendation_agent_client.py` | 已封装 HTTP 调用（/recommendations/alternatives） |
| 返回行程给成员一 | `PlanningAgent._build_result()` 返回 `PlanningAgentResult` | 包含行程、策略、预算、校验结果 |
| 前端组件集成 | `frontend/src/components/` 下 6 个 Vue 组件 | 成员一统一组装到页面布局 |

## 五、合并步骤建议

### 第一阶段：统一公共 Schema

三人编码前必须确保引用同一套 Pydantic 模型，不得各自定义同名对象：

```text
TravelRequest          — 行程需求
RecommendationContext  — 推荐上下文
ExplicitConstraint     — 明确硬约束
SemanticPreference     — 隐含偏好
Place                  — 地点（景点/酒店/餐厅统一模型）
RouteResult            — 路线结果
ItineraryItem          — 行程项
Itinerary / ItineraryDay — 行程
BudgetSummary          — 预算明细
HardConstraintEvaluation — 硬约束校验结果
SoftPreferenceEvaluation — 软偏好评价
ModificationRequest    — 修改请求
TripDiff               — 版本差异
AgentTrace             — 执行轨迹
统一响应格式 / 统一错误码
```

你的 `schemas/` 目录已是最完整的基准，建议以此为公共标准。

### 第二阶段：后端 API 合并

```text
同一 FastAPI 应用，不同前缀挂载：

成员一：/api/v1/sessions, /api/v1/chat, /api/v1/workflows, /api/v1/rag
成员二：/api/v1/recommendations, /api/v1/places, /api/v1/poi, /api/v1/routes
成员三：/api/v1/itineraries, /api/v1/trips
公共：  /api/v1/health
```

### 第三阶段：前端组件集成

```text
成员一搭建 Vue 项目框架、路由、布局
成员一在自己的页面视图中引用：
  - 成员二的 TripMap.vue
  - 成员三的 TripTimeline.vue、BudgetPanel.vue 等 6 个组件
统一通过 Pinia store 管理数据
统一通过 API 封装（api/ 目录）调用后端
```

### 第四阶段：端到端联调

```text
1. 确保各成员 Mock 数据对齐同一套 Schema
2. 成员一工作流依次调用成员二、成员三
```

## 七、数据规范统一约定

| 项目 | 约定 |
|------|------|
| 日期格式 | `YYYY-MM-DD` |
| 时间格式 | `HH:MM` |
| 距离单位 | 米 |
| 时长单位 | 分钟 |
| 金额单位 | 元 |
| 坐标系 | GCJ-02 |
| 坐标顺序 | 经度在前、纬度在后 |

| 高德标识 | `poi_id` |
| 缺失值 | `null`（禁止使用 `""`、`"未知"`、`"N/A"`、`-1`） |
| 枚举命名 | 英文小写下划线（如 `create_trip`、`modify_trip`） |

## 十、总结

你的模块（成员三）是系统的**智能决策核心**：

- 成员一负责 **"理解用户说什么"** — 对话、意图、需求
- 成员二负责 **"有哪些资源可选"** — 景点、酒店、餐厅推荐
- 你负责 **"这些资源怎么组合最好"** — 行程规划、校验、调整

你输出的是一个带完整校验、预算控制和版本管理的**可执行行程**，通过 6 个 Vue 组件在前端直观展示给用户。

合并方式就是**接口对接**：你的 `plan()` 输入来自成员二，`modify()` 输入来自成员一，输出返给成员一，前端组件由成员一统一布局。代码层面各成员按目录分离，运行时通过 API 调用串联。
