## 一、核心定位（v2 关键变化）

成员三负责一个**大模型主导的行程规划与调整 Agent**，回答：

> 成员二推荐的地点应该如何组合成一份可执行行程

| 维度 | v1（旧） | v2（新） |
|------|---------|---------|
| 定位 | 功能模块负责人 | **行程规划与调整 Agent** |
| LLM 角色 | 仅生成自然语言说明 | **大模型主导隐含偏好判断**（"不要太累""经典小众结合"等） |
| 校验 | 9 项 Python 规则 | **两类**：`HardConstraintValidator`（Python） + **`ItineraryPreferenceCritic`（LLM）** |
| 循环 | 自动调整一次 | **硬约束修复循环（≤2次） + 软偏好优化循环（≤1次）** |
| 输入 | `Place[]` + `RouteResult[]` | 额外接收 `RecommendationContext`、`RecommendationPolicy`、`original_text`、`semantic_preferences` |
| 输出 | `Itinerary` + `EvaluationResult` | 新增 `ItineraryPlanningPolicy`、`SoftPreferenceEvaluation` |

### 三大原则

```text
成员一负责保留和传递完整语义。
成员二由大模型判断哪些资源适合用户。
成员三由大模型判断这些资源应如何组合。

本地规则只处理客观事实、明确硬约束、数值计算和输出合法性。
```

## 二、职责边界

### 成员三负责

| 类别 | 内容 |
|------|------|
| **大模型判断** | "不要太累""轻松一点""经典小众结合""尽量多看主要景点"、每日主题、地点组合、访问顺序、活动数量、缓冲时间、软偏好优先级、冲突取舍、修复策略 |
| **Python 规则** | 开放时间、路线距离/耗时、坐标合法性、价格计算、总费用、时间冲突、地点重复、必去/禁止地点、步行上限、饮食禁忌、每日结束时间、place_id/route_id 合法性 |
| **输出** | `Itinerary`、`ItineraryPlanningPolicy`、`BudgetSummary`、`HardConstraintEvaluation`、`SoftPreferenceEvaluation`、`TripDiff`、版本信息 |

### 成员三不得实现

- 重新建设地点数据库
- 重新实现全量景点/酒店/餐厅推荐
- 重新实现高德 POI 搜索
- 重新实现推荐 RAG
- 丢弃原始用户语义后重新猜测需求
- 用固定规则解释隐含偏好（如 `if student: budget=300`）


```
PlanningAgentResult

├── ItineraryPlanningPolicy      # LLM 规划策略（v2 新增）

├── HardConstraintEvaluation     # Python 硬约束校验结果
├── SoftPreferenceEvaluation     # LLM 软偏好评价（v2 新增）
├── TripDiff                     # 版本差异
├── AgentTrace                   # 执行轨迹
└── need_follow_up               # 是否需要追问
```

## 六、两类校验设计

### HardConstraintValidator（Python 规则）

```
明确预算上限 → explicit_budget_validator.py
明确步行上限 → explicit_walking_validator.py
必去地点     → factual_consistency_validator.py
禁止地点     → factual_consistency_validator.py
开放时间     → opening_time_validator.py
路线时间     → route_time_validator.py
活动冲突     → hard_constraint_validator.py（调度）
明确结束时间 → hard_constraint_validator.py（调度）
饮食安全     → food_safety_validator.py
地点合法性   → factual_consistency_validator.py
```

输出 `HardConstraintEvaluation`：
```json
{
  "passed": false,
  "issues": [
    {
      "code": "WALKING_LIMIT_EXCEEDED",
      "severity": "error",
      "day": 2,
      "message": "预计步行9200米，超过用户明确限制8000米"
    }
  ],
  "metrics": { ... }
}
```

### ItineraryPreferenceCritic（LLM 评价）

由大模型判断：
```
是否过于疲劳
是否符合轻松/紧凑节奏
景点是否过度同质化
是否体现当地特色
是否存在无效往返
是否符合学生/家庭/老人等上下文
是否满足用户强调的旅行体验
```

输出 `SoftPreferenceEvaluation`：
```json
{
  "soft_preference_passed": false,
  "issues": [
    {
      "preference": "行程不要太累",
      "assessment": "第二天连续三个高步行强度景点，且午餐时间过短",
      "suggestion": "删除一个次要景点，并增加休息时间",
      "confidence": 0.88
    }
  ]
}
```

## 七、规划循环流程

```
PlanningContext
    ↓
LLM 理解行程层面隐含偏好
    ↓
生成 ItineraryPlanningPolicy
    ↓
LLM 组合每日地点、顺序和节奏
    ↓
工具计算真实路线、费用和时间
    ↓
┌─────────────────────────────────────────┐
│ HardConstraintValidator (Python)        │
│   → 不通过: LLM 修复（最多 2 次）        │
│   → 通过: 进入软偏好评价                 │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ ItineraryPreferenceCritic (LLM)         │
│   → 不满足: LLM 优化（最多 1 次）        │
│   → 满足: 输出最终行程                   │
└─────────────────────────────────────────┘
    ↓
PlanningAgentResult
```

## 八、关键约束速查

| # | 约束 |
|---|------|
| 1 | 距离: **米** / 时长: **分钟** / 金额: **元** |
| 2 | 坐标: **GCJ-02**，顺序: **`[经度, 纬度]`** |
| 3 | 地点统一用 **`place_id`** 关联 |
| 4 | 硬约束修复 ≤ **2 次**，软偏好优化 ≤ **1 次** |
| 5 | 局部重规划**只修改受影响天/时段**，其余锁定 |
| 6 | **禁止** `if student: budget=300` 这类固定规则 |
| 7 | 所有修改生成**新版本**，`parent_version` 链式关联 |
| 8 | 日期 `YYYY-MM-DD` / 时间 `HH:MM` / 缺失值 `null` |
| 9 | 枚举统一英文小写下划线 |
| 10 | 接口不得返回 API Key、完整 Prompt 或内部推理 |
