# 城市自由行智能规划系统完整分工方案

## 一、项目总体架构

本项目由三个相互协作的 Agent 构成：

```text
用户自然语言输入
        ↓
成员一：需求理解与对话 Agent
        ↓
RecommendationContext
        ↓
成员二：旅游资源推荐 Agent
        ↓
RecommendationAgentResult
        ↓
成员三：行程规划与调整 Agent
        ↓
PlanningAgentResult
        ↓
成员一组织最终回复并交给前端展示
```

三个 Agent 的核心职责分别是：

```text
成员一：理解用户说了什么，并保留完整语义
成员二：判断哪些旅游资源适合用户
成员三：判断这些资源应该如何组合成行程
```

系统需要体现：

```text
Chatbot
RAG
Intent Detection
Agent
Tool Call
Workflow
Branch
Loop
多 Agent 协作
来源追溯
结果校验
```

# 二、系统统一设计原则

## 1. 隐含偏好交给大模型

需要结合自然语言和上下文理解的内容，由大模型判断，例如：

```text
预算不要太高
酒店舒服一点
景点不要太普通
行程不要太累
适合学生
适合带老人
想体验当地生活
不想一直赶路
交通方便比最低价格重要
可以为特别值得的体验多花一点
```

这类条件不能写成本地固定规则。

禁止：

```python
if traveler_type == "student":
    hotel_budget_per_night = 300
```

因为“学生”只是一个上下文信号，不能直接等价为固定消费额度。

---

## 2. 客观事实交给工具和程序

以下内容必须通过数据库、地图接口或程序计算：

```text
地点是否真实存在
地点是否位于目标城市
景点门票
酒店价格
餐厅人均价格
经纬度
开放时间
道路距离
路线耗时
地点是否重复
活动时间是否冲突
总预算计算
```

数据来源：

```text
Neo4j：结构化旅游资源数据
RAG：历史、特色、注意事项及来源
高德地图：POI、坐标和真实道路路线
Python：数值计算、格式校验和硬约束校验
```

RAG 不负责生成经纬度、真实路线和确定性费用。

---

## 3. 明确硬约束交给本地规则

用户明确提出的条件必须通过程序精确执行，例如：

```text
酒店每晚不能超过500元
总预算不能超过3000元
每天最多步行8000米
故宫必须去
不要去长城
不能吃花生
每天18:00前结束
第二天下午必须安排室内景点
```

规则只处理这种可明确判断的条件。

---

## 4. 软偏好与硬约束必须分开

例如：

```text
“每天最多走8000米”
→ 明确硬约束
→ Python规则校验

“不要走得太累”
→ 隐含软偏好
→ 大模型结合行程指标判断
```

```text
“酒店每晚不超过500元”
→ 明确硬约束
→ Python规则过滤

“酒店不要太贵”
→ 隐含软偏好
→ 大模型结合用户身份、城市和候选价格判断
```

# 四、成员一：需求理解、对话与总工作流

## 1. 核心定位

成员一负责：

```text
用户对话入口
意图识别
明确需求提取
硬约束与隐含偏好分离
会话上下文管理
Agent总工作流编排
前端总体框架和集成
```

成员一不负责决定最终推荐哪些景点、酒店和餐厅，也不负责完整行程组合。

---

## 2. 负责功能

### 2.1 Chatbot 封装

实现：

```text
接收用户消息
保存多轮对话
读取历史上下文
生成会话回复
管理session_id
恢复中断流程
```

---

### 2.2 一级意图识别

一级意图：

```text
create_trip
modify_trip
travel_qa
```

修改子意图：

```text
replace_attraction
delete_place
replace_restaurant
change_hotel
change_budget
change_time
reduce_walking
change_to_indoor
```

---

### 2.3 明确需求提取

提取：

```text
城市
日期
天数
人数
明确预算金额
兴趣
必去景点
禁止景点
饮食偏好
饮食禁忌
明确步行上限
明确每日开始和结束时间
交通方式
旅行节奏
```

输出：

```text
TravelRequest
```

---

### 2.4 硬约束与隐含偏好分离

成员一需要把用户要求分为两类。

#### 明确硬约束

示例：

```json
{
  "field": "hotel_price",
  "operator": "less_than_or_equal",
  "value": 500,
  "scope": "hotel",
  "source_text": "酒店每晚不能超过500元"
}
```

#### 隐含偏好

示例：

```json
{
  "text": "预算不要太高",
  "scope": "overall",
  "source_text": "预算不要太高",
  "emphasis": "normal"
}
```

成员一只负责识别并保留隐含偏好，不负责解释其具体含义。

---

### 2.5 保留用户原始语言

成员一不能只向成员二传递结构化字段。

例如用户说：

```text
我们两个学生去北京三天，预算不要太高，
但毕业旅行可以住好一点，景点不要太普通。
```

成员一必须传递：

```text
用户本轮原话
与推荐相关的历史上下文
明确硬约束
隐含偏好
系统已有假设
仍未解决的信息
```

否则成员二无法正确理解：

```text
学生
毕业旅行
预算不要太高
可以住好一点
```

这些条件之间的关系。

---

### 2.6 构建 RecommendationContext

成员一向成员二发送：

```json
{
  "session_id": "session_001",
  "requirements": {
    "city": "北京",
    "days": 3,
    "people": 2,
    "total_budget": null
  },
  "original_text": "我们两个学生去北京三天，预算不要太高，但毕业旅行可以住好一点",
  "conversation_context": [],
  "explicit_hard_constraints": [],
  "semantic_preferences": [
    {
      "text": "同行人员为学生",
      "scope": "overall"
    },
    {
      "text": "预算不要太高",
      "scope": "overall"
    },
    {
      "text": "毕业旅行可以住好一点",
      "scope": "hotel"
    }
  ],
  "assumptions": [],
  "unresolved_fields": []
}
```

---

### 2.7 追问管理

成员一负责：

```text
判断关键字段是否缺失
向用户发出追问
保存待回答状态
接收补充回答
更新 RecommendationContext
恢复工作流
```

成员二或成员三可以返回：

```json
{
  "need_follow_up": true,
  "follow_up_question": "住宿更重视价格，还是位置和舒适度？",
  "follow_up_reason": "当前偏好优先级不明确"
}
```

但真正与用户交互仍由成员一负责。

---

### 2.8 总工作流编排

新建行程：

```text
用户输入
→ 意图识别
→ 明确需求提取
→ 硬约束和隐含偏好分离
→ 判断是否追问
→ 构建 RecommendationContext
→ 调用成员二推荐 Agent
→ 接收推荐资源
→ 调用成员三规划 Agent
→ 接收完整行程
→ 组织最终回复
```

修改行程：

```text
用户修改要求
→ 识别 modify_trip
→ 生成 ModificationRequest
→ 调用成员三规划 Agent
→ 成员三必要时调用成员二获取替代地点
→ 返回新版本和修改差异
```

旅游问答：

```text
用户问题
→ 识别 travel_qa
→ 调用 RAGService
→ 返回回答、来源、证据和页码
```

# 五、成员二：旅游资源推荐 Agent

## 1. 核心定位

成员二负责一个完整的：

```text
大模型主导的旅游资源推荐 Agent
```

成员二负责回答：

```text
哪些景点适合用户
哪些酒店适合用户
哪些餐厅适合用户
需要哪些替代地点
```

成员二不负责决定这些地点具体安排在第几天几点。

---

## 2. 推荐 Agent 工作流程

```text
RecommendationContext
        ↓
大模型理解资源层面的隐含偏好
        ↓
生成 RecommendationPolicy
        ↓
大模型决定调用哪些工具
        ↓
查询 Neo4j 候选资源
        ↓
按需调用 RAG、高德POI、路线和价格统计工具
        ↓
大模型比较景点、酒店和餐厅候选
        ↓
大模型进行推荐反思
        ↓
规则校验客观事实和明确硬约束
        ↓
输出 RecommendationAgentResult
```

---

## 3. 大模型负责的内容

```text
理解“预算不要太高”
理解“景点不要太普通”
理解“适合学生”
理解“酒店舒服一点”
判断条件优先级
决定推荐标准
决定是否调用RAG
决定是否需要路线比较
决定候选不足时放宽什么软条件
综合比较候选
决定最终推荐结果
生成个性化推荐理由
检查候选是否过于相似
```

---

## 4. 推荐工具

### 4.1 CandidateSearchTool

查询 Neo4j 中的：

```text
景点
酒店
餐厅
分类
区域
价格

```

工具只返回候选事实，不直接决定最终推荐结果。

---

### 4.2 RAGEvidenceTool

获取：

```text
景点特色
历史背景
文化信息
适合人群
游览建议
注意事项

```

---

### 4.3 POISearchTool

调用高德获取：

```text
poi_id
经纬度
地址
城市
区县
地点类型
```

同名 POI 必须返回候选让用户确认，不能默认选择第一条。

---

### 4.4 RouteTool

获取：

```text
步行路线
驾车路线
批量路线
距离
耗时
Polyline
```

高德失败时允许使用直线距离估算，但必须设置：

```json
{
  "source": "straight_line_estimation",
  "verified": false,
  "warning": "路线未经真实道路验证"
}
```

---

### 4.5 PriceStatisticsTool

提供：

```text
酒店价格分布
餐厅人均价格分布
景点门票价格分布
```

大模型据此结合用户语境理解：

```text
经济型
中等预算
不要太贵
性价比高
```

而不是使用固定金额。

---

## 5. 成员二的规则职责

只负责：

```text
地点是否位于指定城市
place_type是否正确
明确预算上限是否突破
明确禁止地点是否出现
明确饮食禁忌是否冲突
POI是否有效
经纬度是否合法
路线来源是否合法
输出是否符合Schema
```

不负责：

```text
学生应该花多少钱
情侣应该去哪些景点
老人应该走多少公里
固定兴趣权重
固定预算权重
“特色”必须等于“小众”
```

---

## 6. 推荐循环

```text
大模型推荐
→ 硬约束和事实校验
→ 未通过
→ 将具体问题返回大模型
→ 大模型重新选择
→ 再次校验
```

最大重试次数建议：

```text
2次
```

推荐 Critic 检查：

```text
是否忽略用户主要偏好
候选是否过于相似
推荐理由是否有证据
是否存在更合理候选
是否把估算路线当作真实路线
```

# 六、成员三：行程规划与调整 Agent

## 1. 核心定位

成员三负责回答：

```text
成员二推荐的地点应该如何组合成一份可执行行程
```

成员三同样采用：

```text
大模型主导隐含偏好判断
规则处理客观事实和明确硬约束
```

成员三不重新实现景点、酒店、餐厅推荐，也不重新建设地点数据库。

---

## 2. 成员三输入

成员三接收：

```text
TravelRequest
RecommendationContext
RecommendationPolicy
Place[]
RouteResult[]
explicit_hard_constraints
original_text
conversation_context
```

不能只接收 `Place[]`，否则：

```text
不要太累
经典和小众结合
想多体验当地生活
不想一直赶路
```

等语义会丢失。

---

## 3. 行程规划 Agent 工作流程

```text
PlanningContext
        ↓
大模型理解行程层面的隐含偏好
        ↓
生成 ItineraryPlanningPolicy
        ↓
大模型组合每日地点、顺序和节奏
        ↓
工具计算真实路线、费用和时间
        ↓
规则检查客观事实和明确硬约束
        ├─ 未通过 → 大模型修复
        └─ 通过
              ↓
大模型评价隐含偏好满足程度
        ├─ 不满足 → 大模型优化
        └─ 满足
              ↓
输出最终行程
```

## 4. 大模型负责的内容

```text
理解“不要太累”
理解“行程轻松一点”
理解“不要一直赶路”
理解“经典和小众景点结合”
理解“尽量多看主要景点”
决定每天的主题
决定地点组合
决定访问顺序
决定每天安排多少活动
决定休息和缓冲时间
决定哪些软偏好优先
决定发生冲突时牺牲什么
决定如何修复不合理行程
```

例如用户说：

```text
带老人去北京，行程不要太累，但主要景点尽量看到。
```

大模型应理解：

```text
核心景点优先
减少次要景点
避免连续高强度活动
减少跨城区往返
在主要景点之间加入低强度活动或休息
不能简单地把所有景点数量减少到固定值
```

不能写成：

```python
if has_elderly:
    attractions_per_day = 2
```

## 5. 本地规则负责的内容

### 5.1 客观事实

```text
景点开放时间
路线距离
路线耗时
地点坐标
价格
总费用
时间是否冲突
地点是否重复
到达时间是否晚于闭馆时间
```

### 5.2 明确硬约束

```text
总预算不能超过3000元
每天步行不能超过8000米
故宫必须去
长城不能去
每天18:00前结束
第二天下午必须室内
```

### 5.3 数据合法性

```text
行程项是否引用真实place_id
route_id是否存在
时间格式是否正确
金额是否计算正确
地点是否存在有效POI
```

现有接口文档中开放时间、预算、路线耗时、必去景点、步行限制等均属于需要确定性检查的项目。

# 十、完整业务流程

## 1. 新建行程

```text
用户输入
→ 成员一识别 create_trip
→ 成员一提取结构化需求
→ 成员一分离硬约束和隐含偏好
→ 成员一构建 RecommendationContext
→ 成员二理解资源推荐层面的隐含偏好
→ 成员二调用 Neo4j、RAG、高德工具
→ 成员二输出景点、酒店、餐厅和路线
→ 成员三理解行程组织层面的隐含偏好
→ 成员三生成初始行程
→ 程序计算路线、时间和费用
→ 程序检查明确硬约束
→ 大模型评价软偏好
→ 必要时调整
→ 成员一组织最终回复
```

## 2. 修改行程

```text
用户提出修改
→ 成员一识别 modify_trip
→ 成员一生成 ModificationRequest
→ 成员三分析受影响部分
→ 需要替代地点时调用成员二

→ 成员三局部重规划
→ 程序重新计算路线和费用
→ 程序检查硬约束

→ 保存新版本
```

# 十三、最终职责总结

| 成员  | Agent         | 负责判断                         | 工具与规则职责                      | 核心输出                        |
| --- | ------------- | ---------------------------- | ---------------------------- | --------------------------- |
| 成员一 | 需求理解与对话 Agent | 用户说了什么、属于什么意图、哪些是硬约束、哪些是隐含偏好 | 会话、状态、接口和总流程                 | `RecommendationContext`     |
| 成员二 | 旅游资源推荐 Agent  | 哪些景点、酒店和餐厅适合用户               | Neo4j、RAG、高德、POI、路线、事实与硬约束校验 | `RecommendationAgentResult` |

最终原则：

```text
成员一负责保留和传递完整语义。

成员二由大模型判断哪些资源适合用户。

成员三由大模型判断这些资源应如何组合。

本地规则只处理客观事实、明确硬约束、数值计算和输出合法性。
```
