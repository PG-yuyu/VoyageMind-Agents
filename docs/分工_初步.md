可以按 **3 人、只负责本次城市自由行系统新增功能** 来分工。现有 Chatbot 和 RAG 不再重新开发，只做接口封装与业务适配。功能清单本身也明确提出复用现有混合 RAG 的文档处理、检索、重排和来源追溯能力。

## 一、公共复用模块，不单独计入开发量

现有项目封装成两个公共服务：

```text
ChatbotService
├─ 多轮消息管理
├─ 历史消息读取
└─ 基础模型调用

RAGService
├─ 文档上传与解析
├─ 文本切分
├─ 向量检索
├─ 重排
├─ 来源追溯
└─ 知识问答
```

本次只需要增加旅游业务适配，例如：

```python
chatbot_service.chat(messages, context)

rag_service.query(
    question="故宫游览需要注意什么？",
    category="attraction"
)
```

注意：**复用不等于完全不用修改**。仍然需要统一输入输出格式、处理异常，并让 RAG 返回来源文档、证据片段和页码，但不能再花时间重写向量库、切分和检索逻辑。

# 二、三人具体分工

## 成员一：对话、意图识别与 Agent 总流程

### 负责功能

1. 封装现有 Chatbot。
2. 三类一级意图识别：

   * 新建行程；
   * 修改方案；
   * 旅游问答。
3. 用户需求结构化提取：

   * 城市、天数、人数；
   * 预算；
   * 兴趣；
   * 必去和不去景点；
   * 时间、交通、步行限制等。
4. 缺失信息判断和追问。
5. 会话状态和当前行程上下文。
6. Agent 总工作流：

   * Workflow；
   * Branch；
   * Loop；
   * Tool Call 调度。
7. 接入现有 RAG：

   * 旅游问答分支；
   * 推荐依据检索。
8. Agent 执行轨迹记录。
9. 前端对话区、需求卡片、执行过程面板。

### 主要流程

```text
用户输入
→ 意图识别
→ 新建 / 修改 / 问答分支
→ 调用相应 Agent 或工具
→ 更新会话状态
→ 返回结构化结果
```

### 输出接口

```json
{
  "intent": "create_trip",
  "requirements": {
    "city": "北京",
    "days": 2,
    "people": 2,
    "total_budget": 2500,
    "interests": ["历史建筑"]
  },
  "missing_fields": [],
  "session_id": "xxx"
}
```

## 成员二：旅游资源、地图、路线与数据库

### 负责功能

1. 景点、酒店、餐厅数据结构设计。
2. SQLite 或 Neo4j 中的旅游资源数据维护。
3. 景点推荐工具。
4. 酒店推荐工具。
5. 餐厅推荐工具。
6. 高德 POI 搜索。
7. 高德步行、驾车路线规划。
8. 同名 POI 候选确认。
9. 路线缓存。
10. 路线异常降级：

    * 查询缓存；
    * 直线距离估算；
    * 标记“未经真实道路验证”。
11. 地图展示：

    * Marker；
    * Polyline；
    * 信息窗口；
    * 当前地点高亮。
12. 地点数据的简化管理页面。

### 主要流程

```text
结构化需求
→ 查询本地地点数据
→ RAG 补充推荐依据
→ 高德确认 POI 与坐标
→ 筛选景点、酒店、餐厅
→ 计算地点间路线
→ 返回候选资源
```

RAG 只提供景点特色、历史背景和注意事项；坐标、路线与距离必须由地图工具或确定性数据提供，不能让大模型生成。功能清单也明确区分了 RAG 与精确坐标、实时路线、费用计算的责任。

### 输出接口

```json
{
  "place_id": "attraction_001",
  "name": "故宫博物院",
  "type": "attraction",
  "poi_id": "B000A8UIN8",
  "longitude": 116.397,
  "latitude": 39.916,
  "ticket_price": 60,
  "duration_minutes": 180,
  "open_time": "08:30",
  "close_time": "17:00",
  "recommendation_reason": "符合历史建筑偏好"
}
```

路线接口：

```json
{
  "origin_id": "hotel_001",
  "destination_id": "attraction_001",
```

## 成员三：行程规划、预算校验与动态调整

### 负责功能

1. 1～3 日行程规划。
2. 必去景点优先安排。
3. 景点、餐厅、酒店的时间组合。
4. 酒店作为每日出发和返回锚点。
5. 餐饮时段插入。
6. 路线耗时写入时间轴。
7. 预算计算：

   * 酒店；
   * 门票；
   * 餐饮；
   * 交通。
8. 确定性规则检查：

   * 开放时间；
   * 时间冲突；
   * 路线时间；
   * 预算；
   * 必去景点；
   * 重复地点；
   * 步行限制；
   * 饮食禁忌；
   * 每日结束时间。
9. 自动调整一次。
10. 用户主动修改后的局部重规划。
11. 修改前后对比。
12. 行程版本保存。
13. 时间轴、预算图表、评价结果前端展示。

### 主要流程

```text
候选地点与路线
→ 生成初始行程
→ 确定性规则检查
→ 未通过
→ 定位问题
→ 局部调整一次
→ 重新检查
→ 输出最终行程
```

这里不能只让大模型“看起来合理”地生成行程。开放时间、预算、步行距离和时间冲突等必须由 Python 规则完成，模型主要用于生成调整策略和自然语言说明。功能清单已经明确将这些项目划入确定性检查。

### 输出接口

```json
{
  "days": [
    {
      "day": 1,
      "items": [
        {
          "start_time": "09:00",
          "end_time": "12:00",
          "place_id": "attraction_001",
          "activity": "游览故宫"
        }
      ],
      "walking_distance_km": 6.5,
      "cost": 420
    }
  ],
  "total_cost": 2380,
  "evaluation": {
    "passed": true,
    "issues": []
  }
}
```

```json
  "reason": "用户要求改为室内景点",
  "cost_change": -20,
  "distance_change_km": -3.1
}
```

# 三、三人之间的接口关系

```text
成员一
用户输入、意图、结构化需求
        ↓
成员二
候选景点、酒店、餐厅、POI、路线
        ↓
成员三
行程生成、预算检查、规则评价、动态调整
        ↓
成员一
组织最终回答、更新会话状态、展示执行轨迹
```

修改方案流程：

```text
成员一：识别修改意图和受影响日期
        ↓
成员三：确定需要替换的行程位置
        ↓
成员二：提供新的地点和路线候选
        ↓
成员三：局部重规划并重新检查
        ↓
成员一：返回修改结果
```

旅游问答流程则不必经过成员二和成员三：

```text
成员一
→ 调用复用的 RAGService
→ 返回回答、来源、证据和页码
```

# 四、公共数据结构必须先统一

三个人开始编码前，先共同确定以下五个对象：

```text
TravelRequest      用户结构化需求
Place              景点、酒店、餐厅
RouteResult        路线结果
Itinerary          完整行程
EvaluationResult   行程评价结果
```

否则容易出现：

* 成员一使用 `total_budget`，成员三使用 `budget`；
* 成员二路线时间使用秒，成员三按分钟计算；
* 地点名称相同但没有统一 `place_id`；
* 前端无法区分模型估算路线和高德真实路线。

建议统一规定：

```text
时间：HH:MM
日期：YYYY-MM-DD
距离：米
时长：分钟
费用：元
坐标：高德 GCJ-02
地点关联：统一使用 place_id
```

# 五、建议暂不纳入三人核心分工的功能

当前 P0 功能数量对于三人来说仍然偏多。若开发周期只有一周，不建议同时完整实现后台管理、浏览器定位、公交路线、天气、导出和复杂版本管理。功能清单已将当前位置、公交、天气、雨天替换和导出列为时间充足后再完成的 P1 功能。

优先保证：

```text
三类意图
需求提取
RAG 问答
景点/酒店/餐厅推荐
1～3 日行程
高德 POI 和路线
地图与时间轴
预算和规则校验
一次自动调整
用户主动修改
局部重规划
修改前后对比
Agent 执行轨迹
```

这种分工也能完整体现层次二要求的 Chat-bot、RAG、Intent Detection、Agent、Tool Call、Workflow、Branch 和 Loop，同时后端与模型端由小组成员手工完成。

## 最终分工概括

| 成员  | 核心职责                           | 前端区域           |
| --- | ------------------------------ | -------------- |
| 成员一 | 对话、意图、需求提取、状态、Agent 总流程、复用模块接入 | 对话区、需求卡片、执行轨迹  |
| 成员二 | 地点数据、资源推荐、高德 POI、路线、缓存、地图      | 地图、地点卡片、路线展示   |
| 成员三 | 行程规划、预算、规则校验、自动调整、局部重规划、版本对比   | 时间轴、预算、评价、修改对比 |

这比按照“一个人前端、一个人后端、一个人模型”划分更合理，因为每个人都有明确可独立验收的完整业务模块，也能减少最后集中联调时互相等待的问题。
