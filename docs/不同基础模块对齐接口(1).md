# 城市自由行智能规划系统接口设计

## 1. 接口设计目标

本项目由三人并行开发，现有 Chatbot 和 RAG 项目不重新开发，只进行服务化封装和旅游业务适配。

三人职责关系如下：

| 成员  | 主要职责                                            |
| --- | ----------------------------------------------- |
| 成员一 | 对话交互、意图识别、需求提取、会话状态、工作流编排、Chatbot/RAG 接入、前端总体集成 |
| 成员二 | 景点/酒店/餐厅推荐、高德 POI、路线规划、路线缓存、地图可视化               |
| 成员三 | 1～3 日行程规划、预算核算、规则校验、自动调整、局部重规划、版本对比             |

系统需要覆盖三类一级意图：新建行程、修改方案、旅游问答，并包含 Agent、工具调用、工作流、分支和循环。

---

# 2. 总体调用流程

## 2.1 新建行程

```text
用户输入
→ Chatbot 接收消息
→ 意图识别
→ 需求提取
→ 缺失信息判断
→ 景点/酒店/餐厅推荐
→ POI 信息确认
→ 路线计算
→ 行程规划
→ 预算与规则校验
→ 自动调整一次
→ 保存行程
→ 返回前端展示
```

## 2.2 修改行程

```text
用户输入修改要求
→ 意图识别为修改方案
→ 解析修改对象和约束
→ 定位受影响日期或行程项
→ 获取替代地点
→ 重新计算相邻路线
→ 局部重规划
→ 完整方案重新校验
→ 保存新版本
→ 返回修改前后对比
```

## 2.3 旅游问答

```text
用户输入问题
→ 意图识别为旅游问答
→ 调用封装后的 RAG 服务
→ 检索、重排和生成回答
→ 返回回答、来源、证据和页码
```

知识库没有足够依据时，必须明确返回“当前知识库中没有找到足够依据”，不得伪造来源。

# 3. 全局接口规范

## 3.1 基础路径

```text
/api/v1
```

## 3.2 数据格式

```text
Content-Type: application/json
编码：UTF-8
```

## 3.3 日期与时间

| 数据   | 格式           |
| ---- | ------------ |
| 日期   | `YYYY-MM-DD` |
| 时间   | `HH:MM`      |
| 完整时间 | ISO 8601     |
| 时长   | 整数分钟         |

## 3.4 单位

| 字段    | 单位     |
| ----- | ------ |
| 距离    | 米      |
| 步行限制  | 米      |
| 时长    | 分钟     |
| 金额    | 元      |
| 经纬度   | GCJ-02 |
| 经纬度顺序 | 经度、纬度  |

## 3.5 缺失值

统一使用：

```json
null
```

禁止混用：

```text
""
"未知"
"N/A"
-1
```

## 3.6 枚举命名

接口字段和枚举统一使用英文小写下划线，例如：

```text
create_trip
modify_trip
travel_qa
```

# 16. 必须统一的实现约束

1. 所有地点必须使用唯一 `place_id`，不能用地点名称作为主键。
2. 高德地点同时保存 `poi_id`。
3. 坐标统一使用 GCJ-02。
4. 坐标顺序固定为经度在前、纬度在后。
5. 距离统一使用米。
6. 时长统一使用分钟。
7. 金额统一使用元。
8. 地点数据保存单价，预算模块计算总价。
9. 推荐结果只提供候选，不直接生成完整行程。
10. 行程规划不重复实现景点、酒店和餐厅推荐。
11. RAG 负责知识依据，不负责坐标、真实路线和确定性费用。
12. 行程规则校验由 Python 代码完成。
13. 自动调整最多一次。
14. 用户修改采用局部重规划，不重新生成整份方案。
15. 高德失败时允许估算，但必须标记 `verified=false`。
16. 接口不得返回 API Key、完整 Prompt 或内部推理过程。
17. 所有修改都生成新版本，不直接覆盖旧版本。
18. 前端统一通过公共 API 客户端调用后端，禁止组件内散落请求地址。

---

# 17. 第一阶段必须先冻结的接口

为了确保三人能同时开发，以下接口必须在编码前确定，不应随意修改：

```text
TravelRequest
Place
RouteResult
ItineraryItem
Itinerary
BudgetSummary
EvaluationResult
ModificationRequest
TripDiff
统一响应格式
统一错误码
```

其中最关键的模块调用顺序为：

```text
成员一输出 TravelRequest
→ 成员二输出 Place[] 和 RouteResult[]
→ 成员三输出 Itinerary 和 EvaluationResult
→ 成员一统一组织响应
```

后续确需修改公共字段时，必须由三人共同确认，并同步修改接口文档、Schema、Mock 数据和前端类型定义。
